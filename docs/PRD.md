# PRD — 지역별 관광 트렌드 분석 플랫폼

## 1. 목적
- 1차 목적: **웹 서비스 배포 경험**을 쌓는다. 기능은 하나만 제대로 만든다.
- 질문: "어느 시군구의 방문수요가 전년 동월대비 급변했고, 그 변화가 날씨 변화와 관련 있을 가능성이 있는가?"

## 2. 범위 (이번 버전)
### 포함
- **변화율 순위 스크롤 박스**: 선택 연월 기준 순위 대상(방문수요 상위 80% 시군구)을 전년 동월대비 변화율 내림차순으로 나열. 화면에 "상위 80%만 나열"이라고 표시. 한 번에 20행이 보이는 높이.
- **시군구 검색(select/option)**: 시군구를 고르면 순위 스크롤 박스가 해당 시군구 행으로 스크롤되고 강조된다. 별도 UI 없음.
- 선택 시군구의 변화율, 날씨 변화(강수일수·월강수량), 평년 이상도 기준 초과 시 "관련 가능성" 표시
- 선택 시군구의 **관광 타입 구성** 비율(TourAPI 타입별 시설 수). 공급 지표임을 명시. 비가 오히려 방문을 늘리는 지역을 사용자가 유추하는 보조 정보
- 규칙 기반 템플릿으로 생성한 해석 문구
- 정적 사이트로 배포

### 제외 (의도적)
- 방문수요 실제값 순위 표 — 한국관광 데이터랩에 이미 파생 데이터가 많음
- 현지인 포함 분석, 외지인/외국인 분리 필터
- 날씨 영향의 긍정/부정 판단

## 3. 데이터
| 데이터 | 출처 | 비고 |
|---|---|---|
| 방문수요 | 한국관광공사 관광빅데이터(데이터랩) 시군구별 방문자 수 | 일 단위 제공(시군구×현지인/외지인/외국인) → 월 합산, 외지인+외국인 |
| 관광 타입 구성 | 한국관광공사 TourAPI | 타입별 시설 수(공급) |
| 날씨 | 기상청 ASOS 월자료(일자료 집계) | 강수일수(1mm 이상 일수), 월강수량 |
| 기간 | 2024-09-01 ~ 2026-08-31 (24개월, 전년 동월대비 12개월치 산출) | 2026-08까지 전부 조회 확인됨. 9월 말일은 미제공이라 2026-08까지로 고정. 확장은 §7 |

## 4. 분석 규칙
- 변화율 = (올해 월 방문수요 − 전년 동월 방문수요) / 전년 동월 방문수요
- 날씨 변화 = 올해 월 속성값 − 전년 동월 속성값
- 날씨 속성: 강수일수(주력), 월강수량(보조). 기온은 쓰지 않는다.
- 순위 대상: 당해 12개월 방문수요 합계 하위 20%는 순위와 select에서 제외 (방문자가 적어 변화율이 크게 튀기 때문)
- 평년 이상도 분류(기상청 월·계절 전망과 같은 3분위, 평년은 1991~2020): 같은 관측소·같은 월의 과거 30년 값(강수일수, 월강수량)을 정렬해 하위 1/3은 "적음", 중간 1/3은 "비슷", 상위 1/3은 "많음"으로 나눈다. 전년과 올해의 분류가 **양 끝으로 갈릴 때(적음↔많음)** "확연한 변화"로 보고 표시. (분류가 조금이라도 다르면 표시하는 방식은 우연히도 약 67%가 표시돼 변별력이 없어 기본값으로 쓰지 않는다. `analysis/config.py`의 `ALERT_MODE`로 바꿀 수 있다.) 구간 전환 방향(예: 적음→많음)을 화면에 함께 보여 준다.
- "관련 가능성"은 날씨 변화가 평년 이상도 기준을 넘을 때만 표시. 문구는 "영향을 미쳤을 가능성"까지만 쓰고 긍정/부정은 쓰지 않는다. 인과가 아님을 화면에 명시.
- ASOS 관측소가 있는 시군구(약 100개)만 날씨 분석을 내고, 나머지는 "날씨 판단 불가"로 표시.
- 해석 문구: 조건문 + 문장 틀로 Python이 생성.

## 4-1. 데이터 정리 규칙 (실제 응답을 보고 정함)
- 방문자 API의 시군구 코드는 2026-07-01 행정구역 개편으로 바뀌었다(광주·전남 12xxx 통합, 인천 구 개편). 광주·전남은 이름이 유일하면 새 코드로 연결하고, 인천처럼 구가 새로 쪼개진 곳은 24개월이 이어지지 않아 분석에서 제외한다.
- 수원시처럼 상위 시와 하위 구가 같이 오는 곳은 이중 집계를 막으려고 시 단위만 쓴다.
- 일자료 중 외국인 행이 비는 시군구는 0으로 합산한다. 월의 모든 날짜가 있어야 그 달을 쓴다.
- ASOS 일강수량이 비어 있으면 강수 없음(0)으로 본다. 단, 실제 결측도 같은 모양이라 약간의 오차가 생길 수 있다.

## 5. 아키텍처
- Python 스크립트가 API를 호출해 분석하고 JSON 산출 → Vite + React로 빌드한 정적 프론트엔드가 JSON만 읽음
- API 키는 `.env`(커밋 금지), 브라우저에 노출하지 않음
- 배포: GitHub Pages(안), 갱신은 월 1회 수동 또는 Actions

## 6. 한계점
- 기상 관측소가 있는 시군구만 날씨를 분석한다. 관측소가 시군구 일부 지점의 날씨만 대표하므로 같은 시군구 안에서도 실제 날씨와 오차가 생길 수 있다.
- 방문수요는 통신·내비 기반 추정치로 실제 방문자 수와 다를 수 있다.
- 비교 기간이 1년뿐이라 우연한 변동(축제 개최, 공휴일 배치, 행사)과 날씨 효과를 분리하지 못한다.
- 평년 이상도는 날씨가 이례적인지를 재는 것이지, 사람이 체감해 관광 계획을 바꿨는지를 재는 것이 아니다. 경계값도 확정할 수 없는 선택이다. 장기간 날씨 변화와 관광수요 추이를 비교한 "관광영향 이상도"는 번거로워 이번에 하지 않았다.
- 실내 관광 중심 지역에서는 비가 오히려 방문을 늘릴 수 있다. 그래서 날씨 변화가 방문수요 변화에 영향을 미쳤을 가능성만 말하고, 긍정적/부정적 영향이라고는 쓰지 않는다.
- 관광 타입 구성은 방문 목적이 아닌 시설 수(공급)다. 단, TourAPI 인증키(KorService2) 승인 전이라 이번 구현에는 포함되지 않았다.
- 2026-07 행정구역 개편으로 인천 일부 구는 분석에서 빠진다.
- 순위 하위 20% 제외 때문에 관측소가 있는 소규모 군 지역 상당수가 순위·검색에서 사라진다.
- 외지인+외국인을 합산한다. 외국인 값은 외지인보다 훨씬 작아 영향이 미미하다고 보고 분리하지 않았다.
- 월 3분위 경계는 30개 값에서 정해져 흔들릴 수 있고, 관측소마다 기록 연수가 30년보다 짧을 수 있다. 건조한 달은 작은 변화에도 구간이 바뀔 수 있다.
- 방문수요 API는 일부 시군구의 외국인 행이 비어 있어 0으로 처리한다.
- 규칙 기반 해석 문구는 문장이 정형적이고 딱딱하다.

## 7. 확장 가능성
- **분석 기간 확대**: 현재 2년치. 3~5년으로 늘리면 경계값을 방문수요 데이터로 보정하고 우연 변동을 줄일 수 있다.
- **관광영향 이상도**: 기상청 30년 평년값 대비 이상도, 또는 장기간 날씨 변화와 관광수요 추이의 비교로 경계값을 보완. 평년 대비 이상도 예보가 계획 철회에 영향을 줄 수 있다는 점도 반영 가능.
- **관측소 확장**: 관측소가 없는 시군구도 주변 50km 안의 가까운 관측소 관측값으로 대체해 날씨 분석을 낼 수 있다.
- **내국인/외국인 분리**: 데이터랩 방문자 데이터가 내·외국인 분리로 제공되므로 필터·분리 분석을 추가할 수 있다.
- **해석 문구 고도화**: LLM 등으로 문장을 자연스럽게 확장.
- 방문수요 실제값 순위 표
